# Post-1.0 kernel findings (Phases 81–91)

Notes from the first block of work after the 80-phase roadmap closed. With no
phase list left to follow, the work is driven by the gaps the README's Feature
Maturity table names — starting with the one that made every other rating hard
to trust: nothing in the kernel checked that a solid's *geometry* made sense.

## Phase 81 — the validation gap was wider than the caveat suggested

The README already carried the caveat that the B-Rep validators are
"combinatorial only". Writing `GeometryValidator` and pointing it at the
existing kernel turned that from a caveat into two concrete bugs.

**Sharp cones were degenerate.** `PrimitiveFactory::makeCone` builds box
topology from two 4-point rings. With `topRadius = 0` the top ring's four
points coincide, so the solid carries four zero-length edges around a
zero-area cap. Euler and manifold both pass — nothing in the structural
checks can see it. `MainWindow`'s Cone command asks for exactly that shape
(`makeCone(5, 0, 10)`), so every cone a user inserted was geometric nonsense.
Fixed by giving the sharp case apex topology (base quad + four triangles,
5V/8E/5F), sewn with `SolidSewer`, carrying the same analytic conical surface
the frustum path binds. `makeCone` now also refuses a cone with both radii or
zero height instead of returning a degenerate solid.

**ChamferOp's defect got a precise name.** The pinned defect note said the
volume integrator "disagreed"; the validator says what it disagreed about —
four non-planar loops, two self-intersecting loops and one zero-area face on
the 20mm-box case.

### What the validator does *not* do

Planarity is only asserted for faces whose carrier is planar (no surface, or
a surface whose normal field is constant under sampling). Curved carriers —
cylinders, spheres, tori, fillet blends — are skipped rather than guessed at,
because deciding whether a loop vertex lies *on* a trimmed NURBS patch needs
a closest-point solve whose result is meaningless outside the patch's uv
domain. Two checks are advisory and never fail the gate: edge curves that do
not run between their edge's vertices, and distinct vertices at the same
position (legal at a cone apex or a sewn seam, but usually a missed weld).

## Phase 82 — the chamfer defect was two bugs, not one

The known defect was recorded as a reconstruction problem. It was that, but
the polygon soup handed to the reconstruction was *also* wrong, and the second
bug is the one that produced the wrong volume.

1. **Loop construction.** The rewrite walked each original loop half-edge by
   half-edge and pushed `cur->origin` for every non-chamfered edge — including
   at vertices the chamfer had already replaced. A face adjacent to a
   chamfered edge therefore kept the very corner the chamfer cut away,
   alongside the offsets that replaced it. Loop construction is now
   vertex-driven.
2. **Reconstruction.** The soup was replayed through Euler operators by an
   iterative convergence loop that picked target faces by vertex-set
   containment. It terminated with valid linkage — just not the linkage the
   polygons described. Replaced with `SolidSewer`.

**Found in passing: the kernel disagrees with itself about winding.**
`PrimitiveFactory`'s loops are wound *inward* by the Newell convention, while
`SolidSewer` documents its input as outward-wound. Both work, because every
consumer (mass properties, tessellation) normalizes the sign globally — but it
means any code that orients a new face against a fixed "outward" reference is
correct for only half the kernel. ChamferOp's new face is oriented against the
loop area vectors of the two faces it bridges, which is right under either
convention. This is worth a deliberate decision later; for now it is written
down.

FilletOp needed no rebuild: its Phase-61 rewrite already assembles half-edges
strictly from a polygon soup, and it passes the geometric validator across the
constant-radius, variable-radius and corner-blend paths. It picked up the same
output gate.

## Phase 83 — vertex blends are a clipping problem, not a patching one

The natural way to read "chamfer two edges that share a vertex" is that some
extra corner patch has to be generated where the chamfer faces meet. For
planar chamfers that is wrong: the material a chamfer removes is the
half-space beyond its chamfer plane, so the corner is simply the original
corner clipped by the planes of every chamfer meeting there. Three equal
chamfers at a box corner give three planes meeting at a single point, and each
chamfer face becomes a pentagon — no corner face at all.

That reading collapses the whole operation into one code path: clip a local
wedge at each touched vertex, clip each chamfer face by the chamfers at its
ends, sew. The single-chamfer case is the same code with one clipping plane,
so it did not need a separate branch.

The clip runs on a *wedge* — the corner's two loop directions extended far
enough that every cut lands well inside it — rather than on the whole face.
A chamfer plane is unbounded; clipping a whole face by it would let a chamfer
at one corner slice a distant part of a non-convex face.

Verified against inclusion–exclusion volumes for the union of the cutting
prisms (`(1/2)d²L` each, `d³/3` per pair, `d³/4` per triple):

| case | volume |
|---|---|
| one edge of a 10³ box, d = 2 | 980 |
| two edges at a corner | 962⅔ |
| three edges at a corner | 946 |
| all twelve edges (the chamfered cube, 18F/32V) | 808 |

**Remaining limits**, documented in the header rather than papered over: the
offset directions come from the adjacent faces' normals, so an oblique corner's
offsets do not land on the third face's plane — such input is refused by the
geometric gate rather than silently mis-built. The wedge clip assumes a convex
corner. Inner face loops are not carried through the rewrite.

## Phase 84 — the curved-geometry gap was not where the docs said it was

The plan coming out of Phase 83 was analytic surface–surface intersection, on
the strength of the README's note that "curved faces participate as their
inscribed loop polyhedra". Measuring first changed the diagnosis entirely.

`makeCylinder(5, 10)` returned **V=8, E=12, F=6** — box topology — with a
cylindrical NURBS patch bound to its four lateral faces. The solid was a
square prism to every computation in the kernel; only the renderer thought
otherwise. Measured against the analytic values:

| primitive | reported | analytic | error |
|---|---|---|---|
| cylinder r5 h10 | 500.0 | 785.4 | −36% |
| sphere r5 | 192.5 | 523.6 | −63% |
| frustum 2/1 h5 | 23.3 | 36.7 | −36% |
| torus R10 r3 | **0.0** | 1776.5 | −100% |
| cylinder − cylinder (bore) | 320.0 | 502.7 | −36% |

SSI would not have helped any of this: it intersects surfaces, and these
operands' edges are straight lines between four corner points. The surfaces
were decoration.

### Why loop refinement is not the fix either

The obvious cheap fix — follow each edge's curve when extracting the boundary
— was tried and rejected on measurement. The cylinder's rim edges *do* carry
exact quarter arcs (Phase 61), and refining them takes the caps to proper
64-gons. The volume still plateaued at 594 against 785.

The reason is `BoundaryMesh::signedVolume`'s fan from `points[0]`. A fan is
exact for a planar loop and for the enclosed volume of *whatever surface it
describes* — but a refined lateral band is not planar, and the fan from its
first vertex describes a cone from that vertex, not the cylindrical band. The
mesh was watertight (all directed edges paired, area vectors summing to zero)
and still enclosed the wrong volume, because "the volume enclosed by a
non-planar loop" is not defined until you fix a triangulation. Faithful
evaluation of a curved face needs the face tessellated over its carrier, not
its boundary refined.

### What shipped

Faceting at construction, which is the coherent answer for a kernel whose
Boolean, classification and mass-property paths are all faceted anyway. The
B-Rep becomes what the kernel already treats it as, at a resolution the caller
controls, and every consumer converges at once — no second evaluation path, no
watertightness puzzle across faces with different carriers, and no new
inconsistency between what mass properties reports and what Booleans compute.

Volumes now converge from below (an inscribed facet hull is always smaller),
which the tests assert as a *property* — error strictly positive and strictly
decreasing with resolution — rather than pinning a magic number.

### Found in passing: the renderer was drawing each sphere six times

`SolidTessellator` emits a face's whole **untrimmed** carrier whenever that
carrier is curved. With one surface shared across six faces, a sphere was
drawn six times over: 480,000 triangles for a shape that needs 960, and a mesh
enclosing 3× the solid's volume. The cylinder drew its lateral surface four
times, 320,004 triangles against 124. Faceted primitives take the loop path,
so each face is emitted exactly once; both the per-face count and the
mesh/solid volume agreement are now pinned by tests.

### The carrier-versus-intent distinction

Faceting alone would have cost two real features. `MateGeometry` fits a
cylinder to a face's bound surface — a planar facet gives a planar frame, so
concentric mates would need all 32 facets picked. `DrawingDimensioner`'s
radial measurement looks for an edge whose curve is circular — a chord is not.

Both are fixed by separating two things the kernel had conflated:
`topo::Face::surface` is the **carrier**, the surface the loop actually lies
on, and `topo::Face::analyticSurface` (with `topo::Edge::analyticCurve`) is
the **ideal geometry the facet approximates**. Binding the cylinder to a
planar quad as its carrier would have put display and computation back out of
step — exactly the bug being fixed. Recording it separately keeps design
intent available to feature recognition, so one pick on one facet still
resolves the cylinder it belongs to.

These fields are not serialized, so the distinction is lost across a save and
reload; recovering it would mean either persisting them or refitting on load.

### Two consequences, pinned rather than papered over

- **A torus fails `checkEulerFormula()`.** It is genus 1, so `V - E + F` is 0,
  and the check carries no genus term. `checkManifold()` and the geometric
  validator both pass. There is no way to validate Euler for a genus > 0 shell
  without knowing the genus independently, so the tests assert the false
  result deliberately rather than weakening the check.
- **STEP export of a cylinder no longer emits a rational cylindrical
  surface.** The facets are planar, so the file is exactly the model in
  memory. Writing the recorded analytic surface would put a cylindrical
  carrier under a planar quad loop — geometry the file would contradict.
  Emitting analytic faces means un-faceting on export: a real STEP-fidelity
  feature, and a separate one.

## Phases 85–86 — the blends could not act on what Phase 84 built

Faceting the primitives immediately raised the question of whether the blend
operations still worked on them. They did not, and the reasons were defects
rather than missing features.

### Capacity checks were measuring a proxy

Both ops capped the offset at half the shortest edge of the adjacent face.
That is a stand-in for "do not overrun the neighbouring geometry"; it holds
for a box and collapses on faceted geometry, where the shortest edge is the
facet chord. On a 32-sided cylinder of radius 5 the chord is 0.98, so every
chamfer over 0.49 was refused — while the geometry is in fact exact past 4.9.
It was wrong for boxes too, rejecting a 6mm chamfer on a 10mm cube that builds
correctly and integrates exactly.

What actually bounds the offset is how far the face reaches along the offset
direction. That is a *necessary* condition — it never rejects a distance that
would have worked — and the geometric gate added in Phase 82 is what does the
guaranteeing. The usable range on a cylinder rim went from 0.49 to the cap's
inradius (4.976), bounded by geometry instead of a heuristic.

### Three tolerances, three different meanings

The stubborn part was a set of refusals reading "self-intersecting loops" at
moderate chamfer distances. Tracing them found no crossing at all: a loop
segment of **1.075e-7**.

Three components disagreed about what one vertex is:

| component | tolerance |
|---|---|
| the clip's deduplication | 1e-9 × scale |
| `SolidSewer`'s weld | 1e-7, absolute |
| `GeometryValidator`'s degeneracy test | relative to the loop's extent (≈1e-6 here) |

A 1.075e-7 segment is therefore too long to weld, too short to be a real edge,
and reads as degenerate — so it sewed as legal and validated as broken. The
clip now deduplicates against the loop's extent, which is the scale the
validator uses and the scale the inputs are actually built to: an offset
shared by two edges is only equal to within the rounding of two independent
constructions.

Two supporting fixes came out of the same trace. Intersections are snapped to
the endpoint they land on, because a cut through an existing vertex recomputes
that vertex as `cur + (nxt - cur) * t` with t at one end of its range, where
cancellation leaves it a fraction of a micron off. And a segment nearly
parallel to the clip plane no longer has an intersection computed at all: the
denominator there is the difference of two nearly equal signed distances, so
the result is noise rather than a point.

**Worth remembering:** an absolute tolerance and a scale-relative one will
disagree somewhere, and the gap is exactly where the confusing bugs live.

### The fillet had Phase 84's disease

Checking FilletOp for the same capacity problem turned up something larger. A
fillet emitted **one flat quad** joining the two tangent lines, and bound it a
correct rational-quadratic arc surface — degree 2 in V with three control
points, a genuine cylindrical patch. Its *loop* was the chord.

Since every loop-based path in the kernel evaluates a solid from its face
loops, mass properties, Booleans, classification and export all integrated a
chamfer while the renderer drew a fillet. Filleting one edge of a 10mm cube
removes `(1/2)r²L` instead of `r²(1 − π/4)L` — **2.33× too much material, at
every radius**. This is the same shape of defect as the faceted primitives:
an analytic surface pasted onto a coarse loop, so display and computation
disagree. It had gone unnoticed because the fillet tests checked face counts,
TopologyIDs and bound surfaces, but never a volume.

The fix mirrors Phase 84. Blends are faceted across the arc, sampled by
spherical interpolation between the two tangent radii so the points are exact
on the arc rather than a subdivision of the chord, and the arc patch is kept
on `Face::analyticSurface`. Two knock-on pieces were needed: the *end* faces
have to receive the whole arc chain rather than its chord, or the shell does
not close; and corner blends must follow the same samples, since the spherical
patch spans three arcs that are no longer straight.

Volume converges quadratically (0.286% → 0.078% → 0.020% → 0.005% per
doubling at r = 1), which the tests assert as a property — error positive and
strictly decreasing — rather than pinning a number.

Fixing this also surfaced that `analyticSurface` was dropped when a face was
carried through a later operation, so a blend from an earlier fillet lost the
arc it approximates. Faces now propagate it.

## Phase 87 — Revolve enclosed zero volume

After Phases 84 and 86 I recorded a lead: two of three consecutive milestones
had been the same defect — an analytic surface pasted onto a coarse loop — and
the other places the kernel binds a curved carrier were Loft, Sweep, Shell and
Revolve. **Three quarters of that lead was wrong, and worth writing down as
wrong.** Loft, Sweep and Shell all build through `ringstack::makeBilinearPatch`,
which constructs the carrier *from the four corners of the quad it carries*.
Carrier and loop cannot disagree there by construction. The pattern I had
generalized from was not "code that binds curved carriers"; it was "code that
binds a carrier it did not derive from the loop", which is a much smaller set.

Revolve was in that smaller set, and it was worse than the pattern predicted.

### What it did

`Revolve::execute` handled exactly one input: a four-vertex profile turned a
full 360°. For that case it rotated the four profile corners to 0° and 180°,
built an eight-vertex box from the two resulting quads, and pasted a single
`makeTorus` surface onto all six faces — including the two faces that *were*
the profile.

The two quads are mirror images of each other through the axis. The box built
across them is folded through itself, and its enclosed volume is not merely
inaccurate:

| profile (rect r∈[5,10], h∈[0,5], about Y) | measured | Pappus |
|---|---|---|
| volume | **0.000** | 1178.097 |

It passed every check the suite made — `checkEulerFormula()`, `checkManifold()`,
`isValid()`, a non-null `surface` on all six faces, valid TopologyIDs
throughout. Six tests across two files, none of which asked for a volume. The
same blind spot as the fillet tests in Phase 86; it is worth stating plainly
that *"has a NURBS surface" is not a geometric assertion*.

Everything else returned `nullptr`: any partial angle, any profile that was
not a quadrilateral. The UI's Revolve command prompts for an angle between 1°
and 360°, so 359 of its 360 settings produced nothing and reported "profile is
not a closed loop".

### What it does now

A swept ring stack sewn by `SolidSewer` — the Phase 84 pipeline. Any closed
profile of three or more vertices, any angle in (0, 2π], angular resolution
tunable per call and derivable from a chord-sag budget with
`segmentsForTolerance()`, which is the same inversion the primitives use. A
partial turn uses the angular resolution a full turn would, proportionally
fewer steps, so a quarter turn at 32 steps/turn is 8 steps.

Convergence to Pappus, rectangle r ∈ [5,10] × h ∈ [0,5] about Y, exact 1178.097:

| steps | volume | error |
|---|---|---|
| 8 | 1060.660 | −9.968% |
| 16 | 1148.050 | −2.551% |
| 32 | 1170.542 | −0.641% |
| 64 | 1176.206 | −0.161% |
| 128 | 1177.624 | −0.040% |

Exactly 4× per doubling, and always from below — an inscribed polygon can only
undershoot. Partial turns land on the same relative error as the full turn at
equal resolution (−0.161% at 64 steps/turn for a quarter, a half and three
quarters alike), which is the check that the angular-resolution rule actually
holds.

### Three things worth keeping

**Every band is exactly planar.** I expected to need the analytic-carrier
machinery for the oblique bands and was wrong. Take a profile point at radius
`r` and height `h`; rotating it by θ gives another point at the same radius and
height. For a band spanning profile points a and b through angle θ, all four
corners satisfy `p·n = const` for `n = (h_b − h_a)·u(θ/2) + cos(θ/2)(r_a −
r_b)·k`, where `u(θ/2)` is the angular bisector and `k` the axis. So the
sewer's planar carrier *is* the surface the loop lies on, for every band, and
nothing here needs `analyticSurface` to stay honest. The ideals are recorded
anyway — a cylinder for an axis-parallel profile edge, a cone for an oblique
one — because mate frames and radial dimensions resolve through them. A band
sweeping a flat annulus records nothing, because its planar carrier is already
exact and there is no ideal to record; only its rims are approximated, and
those are `Edge::analyticCurve`.

**One test covers three malformed inputs.** The profile must lie in a
half-plane bounded by the axis. Computing each profile point's radial vector
(its component perpendicular to the axis) and requiring all of them to be
non-negative multiples of one direction rejects, in a single pass: a profile
crossing the axis, an axis not lying in the profile's plane, and an axis
parallel to the plane but offset out of it. The last two would otherwise sweep
self-intersecting shells that sew into something plausible-looking.

This retired a test. `RevolveAroundZAxis` revolved an XY-plane rectangle about
the Z axis — the sketch normal — and asserted the result was a valid solid.
That input has no solid of revolution; the profile sweeps within its own plane.
It "passed" only because the old builder ignored the geometry.

**A profile vertex on the axis does not move.** Its band collapses, and
`addQuad` drops the degenerate side, so a triangle touching the axis sweeps a
real cone (261.373 against π·25·10/3 = 261.799 at 64 steps) and closes the hole
that would otherwise make the result genus 1. A full turn *clear* of the axis
is a torus: manifold and closed, but genus 1, so `checkEulerFormula()` rejects
it — the same caveat `makeTorus` carries, now asserted rather than papered
over.

## Phase 88 — accuracy was a compile-time constant

Phases 84 through 87 all end the same way: the solid is faceted, and how
closely it matches the exact shape is decided by a step count. Those phases
gave that count a principled default and a way to derive it from a tolerance
(`segmentsForTolerance()` on both `PrimitiveFactory` and `Revolve`). What they
did not do was make it reachable.

`PrimitiveFeature::execute` called `makeCylinder(m_p0, m_p1)`. `RevolveFeature`
called `Revolve::execute(..., m_featureID)`. `FilletFeature` called
`FilletOp::execute(..., m_featureID)`. Every one of them took the default. The
`segments` and `arcSegments` arguments existed in the kernel and were reachable
from a unit test, and from nowhere else in the product.

The consequences were not subtle:

- A user modelling a precision part had no way to ask for the tighter cylinder,
  through the UI or otherwise. The parameter editor is generic over
  `Feature::parameters()`, and the resolution was not in that map.
- Every saved file replayed at whatever the build-time default was. Change
  `kDefaultSegments` and every existing document changes shape on next open.
- The `.hzpart` format stores the feature tree, not the B-Rep, so a reload
  *replays*. That is why `analyticSurface` and `analyticCurve` survive a round
  trip without being serialized — they are regenerated. It is also why an
  unreachable resolution is a persistence bug and not merely a UI gap: there is
  nothing in the file that records what the part was actually built at.

The fix is small because the interfaces were already there. `parameters()` and
`setParameter()` are the generic parametric contract that both the UI editor
and `NativeFormat` go through, so exposing the count through them made it
editable and persistent in one change rather than two. Validation lives with
the feature: three angular steps is the fewest that bounds a volume, and one
arc chord is the degenerate blend that removes a chamfer's worth of material
rather than a fillet's. A box is exact and so reports no resolution at all and
refuses to be given one — worth doing explicitly, since silently accepting a
meaningless parameter is how a knob becomes folklore.

Serialization needed no version bump. The keys are absent from older files, so
`fObj.contains(...)` leaves the feature's own default standing, which is what
those files were built with. `BinaryFormat` stores the same JSON envelope
inside its FlatBuffers container, so it came along without a change.

The general lesson is worth stating: making something tunable in the kernel is
not the same as making it a property of the model. Phases 84–87 each ended
with a `segments` argument and a satisfied test, and the product still could
not use any value but one.

## Phase 89 — Sweep's "fidelity gap" was a zero-thickness leg

The findings list above closed Phase 88 by calling Sweep's translation-only
transport "a fidelity gap, not the Phase 84 defect", on the grounds that the
bilinear patches pass through the actual corners. That reasoning checked that
carrier and loop agree. It did not check that the loops enclose anything.

Measured, the L-shaped sweep in the test suite — a 2×2 square in the XY plane,
up 10 along Z, then 8 along X — integrates to **40.000** against the 72 a
mitered pipe encloses, and `GeometryValidator` reports **two degenerate
faces**. Translating an XY-plane square along +X moves it edge-on, so the
second leg is a sheet of zero thickness; the 40 is the first leg's 4 × 10.
The test that owned this case asserted V/E/F counts, Euler, manifold,
`isValid()` and a surface on every face. That is now the fourth time in this
note that "has a surface and passes the structural checks" has stood in for a
geometric assertion.

`SweepFeature` had a second, independent defect: `extractPathPoints` took an
arc's start and end points and nothing between, so any arc in a path sketch
was swept across its chord.

### The miter construction

Each segment k sweeps a prism along its direction d_k, cut at both ends. Ring
k+1 is ring k projected along d_k onto the next cutting plane — the bisector
of the turn at an interior point (normal d_k + d_{k+1}), or at the far end the
profile's own normal carried through every turn. Three properties fall out:

- **The frame is rotation-minimizing.** The section the next segment sees is
  the mirror image of the incoming section through the miter plane. Mirroring
  maps d_k to −d_{k+1}, and on the plane perpendicular to d_k it agrees with
  the minimal rotation taking d_k to d_{k+1} on both basis vectors (the turn
  axis, which lies in the miter plane, and its in-plane perpendicular), so
  the two maps are the same. Mitered pipe elbows have been built this way for
  a long time for exactly this reason; the tests check it by asserting the
  far cap of a path turning in three planes is a congruent square centred on
  the end point.
- **Every lateral face is exactly planar**, because its four corners lie on
  two lines parallel to d_k. As with Revolve, no face needs an approximate
  carrier.
- **The volume is exact**, not convergent. A prism cut obliquely at both ends
  has volume (normal section area) × (length of its centroid line between the
  cuts). With the profile's centroid on the path, the sum over segments is
  area × path length to rounding. The tests assert it to 1e-8 on that
  non-planar path, 1e-9 on the L and U paths, and for a profile tilted 30° off
  the path's normal plane (area × cos 30° × length).

Only path *arcs* converge, because they are sampled: at `segments` steps per
turn the chain is shorter than the arc, so the volume approaches area × arc
length from below.

### Folding is a sign test

A turn is too tight when the inside of the profile would have to travel
backwards along the segment to reach the next miter plane. The projection
already computes that distance for every profile point, so the fold test is
that every one is positive. The 1-wide U-turn with a 4-wide profile is
refused; the 10-wide one with a 2-wide profile builds to its exact 120.

`SweepFeature` gained a `segments` parameter following the Phase 88 pattern:
reported by `parameters()`, validated by `setParameter()` (three steps per
turn is the fewest that still turns a circle), written to the part file and
absent-means-default on load.

## Phase 90 — a count is the wrong unit for accuracy

Phase 88 ended with the observation that making something tunable in the
kernel is not the same as making it a property of the model. Phase 90 is the
same lesson one level up: making the count a property of the model is not the
same as making *accuracy* one. A chord spanning 2π/n on a circle of radius r
sags r(1 − cos(π/n)). At the default 32 that is 0.024 on a radius-5 cylinder
and 0.48 at radius 100 — the same setting, twenty times the error. Edit a
cylinder's radius from 5 to 100 and its accuracy silently degrades by that
factor.

`segmentsForTolerance()` had been written for exactly this in Phase 84 and
again in 87, and had no caller outside its own tests.

### The governing radius

A tolerance only means something against a radius, and each feature has to
say which one:

| feature | governing radius |
|---|---|
| cylinder, sphere | its radius |
| cone | the larger of its two radii |
| torus | major + minor, the outer rim, whose chords sag most |
| revolve | the profile vertex farthest from the axis (`Revolve::profileRadius`) |
| sweep | each path arc's own radius, sampled independently |
| fillet | the fillet radius, over the quarter arc its blend spans |

The fillet needed its own inversion (`FilletOp::arcSegmentsForTolerance`)
because its count is chords per blend, not steps per turn. FilletOp only
supports orthogonal corners, so a blend always spans a quarter turn; if
oblique corners are ever supported, the blend angle will have to come from
the corner.

### Two modes, one of them explicit

`chordTolerance` = 0 means "use the count", and setting the count clears the
tolerance, so the last thing the user asked for wins. The file stores both —
the count the tolerance produced, and the tolerance — and the loader applies
them in that order. That is what makes a reloaded part stay in tolerance mode:
a radius edit after reload still re-derives the count, which the round-trip
test asserts.

**Found in passing:** the feature parameter dialog floors every value at
0.001. A tolerance of 0 would have been shown as 0.001 and, for anyone
clicking OK through the dialogs, silently switched on. The floor is 0 for that
field.

## Phase 91 — the surfaces were never on their surfaces

Phase 91 was supposed to be the next Phase 84-style fix (below, as 92), and a
test for it asserted that a point on the ideal cylinder an extruded arc records
lies at the cylinder's radius. It came back at 5.126 on a radius of 5. The
extrude was right; `NurbsSurface::evaluate` was wrong.

The evaluator runs De Boor in two passes: every row as a curve in V, then a
curve across the resulting points in U. A rational row curve returns its
*projected* point, C_i = Σⱼ Nⱼ(v) wᵢⱼ Pᵢⱼ / Wᵢ with Wᵢ = Σⱼ Nⱼ(v) wᵢⱼ, and
the second pass must then weight C_i by Wᵢ to reassemble the tensor-product
quotient. It was given weight 1. For every standard quadric the rational
direction is U (the circle), so the circle was evaluated as a plain quadratic
B-spline through its control polygon — exact at the knots, where the curve
touches its control points, and bulging off the circle between them.

| surface | worst radial error, old | new |
|---|---|---|
| cylinder r5 | 0.303 | 3e-15 |
| sphere r3 | 0.182 | 2e-15 |
| torus 5/2 | 0.425 | 4e-15 |
| cone 30°, h 10 | 0.350 | 3e-15 |

This is the fifth defect in this note that a test had already seen and
written down as acceptable. The sphere test said "the two-pass De Boor
evaluation with product weights introduces small rational approximation error
(~5%), so we use tolerance 0.2 here", and the weighted-surface test said the
pull "is not as strong as a full homogeneous evaluation would give". Both were
describing a bug. A rational evaluation has no approximation error to budget
for; any tolerance wider than rounding on an analytic surface is a finding.

It went unnoticed in the product because the consumers either sample at
knots (mate frames evaluate at u ∈ {min, mid, max}, which for a four-arc
circle are all knots) or stopped relying on curved carriers in Phase 84 (a
faceted primitive's carriers are planar). The display tessellator still
evaluates any curved carrier it is handed, so curved faces arriving without
facets — an imported STEP body's, for one — were drawn bulged.

## Not yet addressed

Analytic surface–surface intersection remains future work, but it is a
fidelity improvement rather than a correctness fix: Booleans on curved solids
produce the right answer to within the operands' facet error.

Open items in this area:

- Filleting a *faceted* edge chain (a cylinder rim) is still refused.
  ChamferOp handles it; FilletOp's vertex blends require exactly three edges
  meeting at a corner, and a rim vertex has two. The chamfer work suggests the
  shape of the fix — treat the chain as one logical edge — but the fillet's
  rolling-ball construction is not a clipping problem.
- `analyticSurface` / `analyticCurve` are still not serialized. For `.hzpart`
  this turns out not to matter: the format stores the feature tree and a reload
  replays it, regenerating both. It matters for any path that carries a B-Rep
  rather than its recipe — STEP import in particular, where a body arrives with
  no analytic geometry attached and mate frames and radial dimensions cannot
  resolve from a single pick.
- Faceting is still applied at construction. Phase 88 made the resolution a
  feature property, so changing it rebuilds the feature at the new count — but
  there is no re-faceting pass over an existing solid, and a solid that reaches
  the kernel without a feature behind it (an imported STEP body, say) keeps
  whatever resolution it arrived with.
- A chord tolerance is per feature. A document-wide default (so a new
  cylinder picks up the part's accuracy rather than 32 facets) would be the
  natural next step, and is a UI decision as much as a kernel one.
- Sweep's miter construction is local: it refuses a turn the profile cannot
  make, but a path that loops back and crosses itself several segments later
  is only caught if the sewn shell fails the geometric gate. A global
  self-intersection test would need the Boolean machinery.
